# lucklyrics-platform

Экземпляр white-label платформы многоканальных продаж: витрина, кабинет продавца,
AI-помощник, синхронизация с маркетплейсом. Код общий для всех продавцов, данные
конкретного — только в `config/brand.json`.

## Команды

```bash
npm test            # 71 проверок, встроенный раннер Node, зависимостей нет
JWT_SECRET=… npm start                    # сервер на :3000; без секрета не стартует
node api/scripts/add-seller.js <логин> <пароль>   # продавец для кабинета
bash web/build.sh   # сборка витрины: подстановка адреса API
```

Node 24 (`.nvmrc`). Тесты гоняются на каждый коммит через CI.

## Правила проекта

1. **Одна точка чтения.** Параметр читается в одном месте, дальше по коду идёт
   результат, а не условие. Проверка: «покажи все места, где читается это значение».
   Больше двух — параметр спроектирован неверно, нужен резолвер.
2. **Бренда нет в коде.** Название и домен продавца не встречаются в исходниках.
   Ловится тестом `no-brand-in-code.test.js` — он уже поймал одну утечку.
3. **Ключи только в окружении.** В браузер не попадают никогда. Модель и площадка
   вызываются сервером, не витриной.
4. **Адаптер полон.** Любой платёжный адаптер реализует все четыре операции,
   включая возврат и статус. Заглушка — тоже.
5. **Остаток честен.** Списание уменьшает ровно на количество, отрицательным не
   становится, сумма продаж по каналам не превышает физический остаток.
6. **Сумму считает сервер.** Витрина показывает расчёт, но не определяет его:
   корзина и заказ идут через одну функцию `catalog.quote`.
7. **Тесты в том же коммите, что и код.** Вынесенные «на потом» не пишутся никогда.
8. **Без ключей — только сухой режим.** Клиент площадки физически не может уйти
   в бой без `MARKETPLACE_CLIENT_ID` и `MARKETPLACE_API_KEY`.

## Авторизация

- Всё про вход — в `api/lib/auth.js`: `register`, `login`, `verify`, `requireSeller`,
  `requireOwner`. `JWT_SECRET` и запись `auth` в хранилище больше никто не читает.
- Пароль — scrypt со случайной солью, токен — свой формат JWT на HMAC-SHA256,
  12 часов. Только `node:crypto`: bcrypt и jsonwebtoken не подключать.
- Нет `JWT_SECRET` (или он короче 32 символов) — сервер не стартует, модуль
  отказывает. Значения по умолчанию нет и не появится.
- Маршрут кабинета оборачивается в `cabinet()` в `server.js`: продавец приходит
  из токена, операция идёт, только если его экземпляр совпадает с `instance.id`,
  иначе 403. Идентификатор из тела или адреса не читается никогда.
- Без входа: каталог, расчёт корзины, `POST /api/orders`, конфиг, тема, живость,
  сам вход. Остальное — через `cabinet()`; новый маршрут кабинета без обёртки — ошибка.
- Неверный пароль и чужой логин — один и тот же ответ `INVALID_CREDENTIALS`.
- В кабинете токен живёт в памяти страницы, не в localStorage.
- Диск площадки размещения эфемерный: пока нет постоянной реализации хранилища,
  продавца заводят заново после каждого развёртывания.

## Хранилище

- `api/lib/store.js` — единственная точка выбора: `storage.provider` в конфиге,
  `STORE_PROVIDER` в окружении перекрывает. Реализации: `file` (папка `DATA_DIR`,
  по умолчанию `data/`) и `memory` (тесты, после перезапуска пусто).
- Интерфейс: `read(name)` → данные или `null`, `write(name, data)`, `update(name, fn)`.
  Изменение того, что уже лежит, — только через `update`: записи одного имени идут
  по очереди, параллельная не теряется. `read` + `write` вместо `update` — ошибка.
- Имена записей: `orders`, `auth`, `catalog`. Модули данных про файлы не знают:
  `fs` в `orders.js`, `auth.js`, `import.js` не появляется.
- Реализация даёт только сырое чтение и запись, очередь и копии — общие
  (`store/serial.js`), поэтому ведут себя одинаково. Тест `store.test.js` гоняет
  один сценарий на всех реализациях — новая реализация добавляется в него.
- Очередь работает внутри процесса. Скрипт и сервер, пишущие одно имя
  одновременно, не защищены — это задача постоянного хранилища.
- Каталог читается из хранилища один раз при старте (`catalog.init`), дальше —
  копия в памяти. Списание остатка меняет копию, а в хранилище она попадает
  только с импортом: после перезапуска остаток — на момент последней записи.
  Закрывается на этапе количественного остатка.

## Импорт каталога

- `api/lib/import.js`, маршрут `POST /api/catalog/import` за `cabinet()`. Тело —
  сам файл, CSV или JSON; `?dryRun=1` — предпросмотр, ничего не пишет.
- Колонки — по названиям, русским и английским, как в коде пекарни: регистр
  и пробелы по краям не важны, берётся первое совпавшее из списка `COLUMNS`.
  Незнакомая колонка сохраняется полем позиции `attrs`. Пустая ячейка значение
  не меняет. Новое название колонки — добавить в `COLUMNS`, а не в разбор.
- Идемпотентность по артикулу: повтор обновляет, не плодит дубли. Одинаковый
  файл — ноль записей.
- Ошибки — списком по строкам («строка 7: цена не число»), разбор не прерывается,
  строки с ошибками пропускаются. Молча подставлять 0 вместо негодного значения
  нельзя: так было в коде пекарни, сюда не переносится.
- Кодировка: UTF-8, иначе Windows-1251 (так сохраняет Excel).

## Чего не делать

- Не читать `config/brand*.json` мимо `api/lib/config.js`.
- Не добавлять цвета в конфиг: палитра выводится из одного акцентного в `brand.js`.
- Не подключать произвольные шрифты: типографика выбирается из набора.
- Не переписывать перенесённый код «под свой стиль» — экономия переноса обнулится.
- Не расширять публичный конфиг служебными полями: наружу уходит только тема,
  тексты, юридические ссылки, валюта, ступени скидки, включённые каналы.
- Не ставить зависимости без необходимости: сейчас их ноль, и это ценность.
- Не коммитить посреди rebase или слияния: перед коммитом `git status` и
  `git grep -n '^<<<<<<<'`. Маркеры конфликта однажды уже ушли в историю.
- Не вставлять данные покупателя в разметку без `esc()`: имя из заказа попадало
  в кабинет как HTML, а там теперь лежит токен.

## Периметр

В работе: витрина, кабинет, AI-помощник, синхронизация с одной площадкой
(оба режима исполнения — свой склад и склад площадки).

Отложено, точки расширения оставлены: вторая площадка, расчёты через внешнюю
систему с эскроу (адаптер-заглушка есть), общий пул остатков вместо буфера,
автовозврат по правилу.

## Принятые решения

- **Наборы — сборка на лету.** У набора своя карточка и своя цена: цена задаётся,
  а не вычисляется из компонентов — наборы поднимают чек. Своего остатка нет,
  склад общий: иначе один товар ведётся дважды и продаётся и в наборе, и отдельно.
  - Доступность набора — минимум по составу: доступность компонента, делённая
    на кратность, с округлением вниз. Доступность компонента — только из
    `availableStock`: буфер учтён там один раз, набор про буфер не знает.
  - Списание атомарно: все компоненты или ни одного, отмена возвращает все.
    Обязателен явный тест: при нехватке одного компонента остальные не списываются.
- **Страховой запас — 2 по умолчанию** (`stock.bufferDefault`), с переопределением
  по позиции. `bufferFor` — резолвер с явным приоритетом: значение у позиции
  в каталоге → `stock.bufferBySku` в конфиге бренда → `stock.bufferDefault`.
  Ближе к товару — побеждает. Все, включая синхронизацию с площадкой,
  спрашивают только `bufferFor`. Сейчас он читает только конфиг; уровень позиции
  добавляется в него же, не рядом.

## Открытые решения

- **AI-помощник в первой волне** — от этого зависит, проектируется ли корзина
