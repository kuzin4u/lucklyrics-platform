# Хранилище

Читать, когда добавляете новую запись данных, пишете реализацию хранилища
(базу) или разбираетесь, где лежат данные экземпляра.

## Интерфейс

- `api/lib/store.js` — единственная точка выбора реализации: `storage.provider`
  в конфиге бренда, `STORE_PROVIDER` в окружении перекрывает.
- Реализации: `file` — файлы `<имя>.json` в `DATA_DIR` (по умолчанию `data/`),
  `memory` — для тестов, после перезапуска пусто.
- `read(name)` → данные или `null`; `write(name, data)` — целиком;
  `update(name, fn)` — `fn` получает текущее и возвращает новое. Обновления одного
  имени идут по очереди, параллельная запись не теряется. Изменение того, что уже
  лежит, — только через `update`: `read` + `write` теряет чужую запись.
- Имена записей: `orders`, `auth`, `catalog`, `stock`. Модули данных не знают про
  файлы: `fs` в `orders.js`, `auth.js`, `import.js`, `stock.js` не появляется.

## Реализации ведут себя одинаково

Реализация даёт только сырое чтение и запись; проверка имени, копии на входе
и выходе и очередь — общие (`store/serial.js`). `store.test.js` гоняет один
сценарий на всех реализациях — новая реализация добавляется туда же и в
`_drivers` в `store.js`. Файловая запись атомарная: временный файл и
переименование, права 600.

## Старт

Каталог и остаток читаются из хранилища при старте (`catalog.init`, затем
`stock.init`), дальше работают копии в памяти, обновляемые после каждой записи.

## Ограничения до постоянного хранилища

- Диск площадки размещения эфемерный: при развёртывании теряются заказы, продавцы,
  каталог и остаток. Временно `DATA_DIR` можно направить на постоянный диск.
- Очередь работает внутри процесса: скрипт и сервер, пишущие одно имя
  одновременно, не защищены. Отдельно не чинится — решается постоянным хранилищем.
- Журнал движений остатка растёт внутри записи `stock` без ограничения.
