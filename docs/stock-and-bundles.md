# Остаток и наборы

Читать при любой работе с остатком, журналом движений, страховым запасом
и наборами: заказы, отмены, импорт, синхронизация с площадкой.

## Остаток — отдельно от каталога

Каталог — описание товара (цена, название, состав), остаток — факт склада: у них
разная частота изменений и разные источники правды. Остаток — запись `stock`
в хранилище: уровни `stock` (свой склад) и `marketplaceStock` (склад площадки)
по позициям. Поля остатка в описании товара никто не читает; `config/catalog.json`
даёт только стартовый остаток, пока записи `stock` нет.

## Чтение и изменение — только `stock.js`

- Читать: `availableStock(sku, channel)`, `canSell`, `level(id)`, `bufferFor(sku)`, `log()`.
- Менять: `reserveMany` (заказ), `releaseMany` (отмена), `setMany` (импорт),
  `adjust` (ручная правка). Проверка и изменение — внутри одного `update`, поэтому
  два заказа на последнюю штуку не проходят оба. Поштучного списания нет.
- `reserveMany(lines, channel)`: сначала проверяются все строки, потом списываются
  все; не прошла одна — не списано ничего. Одинаковые позиции складываются.
- В минус остаток не уходит ни в одной схеме, включая квоты `split`.

## Журнал движений

Каждое изменение: когда, позиция, поле, дельта, до и после, причина (`seed`,
`order`, `cancel`, `import`, `manual`), кто — продавец из токена, ссылка на заказ.
Отвечает на вопрос «почему остаток такой» и станет основой сверки с площадкой.

- `GET /api/stock/log?id=&limit=` — за входом, новые сверху.
- `POST /api/stock/adjust` `{id, value | delta, reason}` — за входом. Без причины —
  `REASON_REQUIRED`, одновременно значение и дельта — `VALUE_OR_DELTA`, в минус —
  `NEGATIVE_STOCK`, у набора — `BUNDLE_HAS_NO_STOCK`.
- Экранов журнала и правки в кабинете пока нет — только эти маршруты.

## Страховой запас

По умолчанию 2. `bufferFor` — единственный источник, приоритет: значение `buffer`
у позиции в каталоге → `stock.bufferBySku` в конфиге бренда → `stock.bufferDefault`.
Ближе к товару — побеждает; ноль у позиции — значение, а не «не задано». Все,
включая синхронизацию с площадкой, спрашивают `bufferFor` и не знают, откуда число.

## Наборы

- Позиция вида `bundle`: состав `[{id, qty}]` и своя заданная цена — наборы
  поднимают чек, цена не складывается из компонентов. Своего остатка нет: иначе
  один товар ведётся дважды и продаётся и в наборе, и отдельно.
- Доступность — минимум по составу: `availableStock` компонента в этом канале,
  делённый на кратность, с округлением вниз. Буфер учтён внутри доступности
  компонентов один раз, набор про буфер не знает.
- В корзине и заказе набор — одна строка со своей ценой. Корзина проверяет общий
  спрос по складу: набор и та же позиция отдельно делят один остаток.
- Заказ хранит оба представления: `items` — как видел покупатель, `reserved` —
  что ушло со склада. Отмена возвращает ровно `reserved`, а не состав набора на
  сегодня; статус пишется раньше возврата, сбой не вернёт товар дважды.
- Набор внутри набора запрещён. Витрина показывает состав в карточке, кабинет —
  набор и списанное в заказе.
