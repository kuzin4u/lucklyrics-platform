# Экземпляр платформы многоканальных продаж

Каркас white-label платформы: витрина, серверный контур, синхронизация с площадкой,
платёжный слой. Значения конкретного продавца живут только в `config/brand.json`.

## Запуск

```bash
cp config/brand.example.json config/brand.json   # заполнить под продавца
cp .env.example .env                              # секреты, в репозиторий не попадают
npm test                                          # 59 проверок, ни одной зависимости
node api/scripts/add-seller.js <логин> <пароль>    # продавец для кабинета
JWT_SECRET=<от 32 символов> npm start              # http://localhost:3000/api/health
```

Витрина: `bash web/build.sh` подставляет адрес API и собирает `index.html`.

## Структура

```
config/brand.json          единственное место с данными продавца
config/brand.<slug>.json   конфиги других продавцов для предпросмотра
config/knowledge.md        база знаний помощника: факты отдельно от обещаний
api/lib/schema.js          проверка конфигурации при старте
api/lib/config.js          единственная точка чтения конфигурации
api/lib/brand.js           слой брендирования: палитра, типографика, логотип, подпись
api/lib/stock.js           единственная точка чтения остатка
api/lib/payments/          адаптеры: интерфейс из четырёх операций
api/lib/marketplace/       клиент площадки с режимом сухого прогона
api/lib/auth.js            вход в кабинет: scrypt, токен HMAC-SHA256, защита записи
api/server.js              каркас: живость, тема, публичный конфиг, журнал намерений
web/assets/                логотип и фавикон экземпляра
web/                       статика витрины, сборка подставляет адрес API
tests/unit/                проверки и инварианты, запускаются на каждый коммит
```

## Брендирование

В конфигурации задаётся **один** акцентный цвет — остальные выводятся: тёмный для
наведения, светлая заливка, цвет текста поверх акцента по контрасту. Пять полей
вместо одного означали бы рассинхрон при первой же смене цвета.

Типографика выбирается из набора (`neutral`, `warm`, `strict`), а не задаётся
произвольным шрифтом: иначе вёрстка каждого экземпляра начнёт жить своей жизнью.

Логотип берётся из `web/assets/`. Файла нет — рисуется текстовый знак, первая
буква названия на акцентном фоне. Сайт можно показать, не дожидаясь дизайнера.

Подпись платформы в подвале — флаг `branding.poweredBy`, включён по умолчанию,
отключается в старшем тарифе.

### Предпросмотр

`config/brand.<slug>.json` открывается ссылкой `?preview=<slug>` — витрина
показывает чужой конфиг, ничего не сохраняя. Так будущий клиент видит свой сайт
до подписания договора. Имя ограничено шаблоном, выход за папку конфигов
невозможен.

## Правила проекта

1. **Одна точка чтения.** Параметр читается в одном месте, дальше по коду идёт результат.
   Проверяется вопросом «покажи все места, где читается это значение».
2. **Бренда нет в коде.** Название и домен продавца не встречаются в исходниках —
   это проверяет тест `no-brand-in-code.test.js`.
3. **Ключи только в окружении.** В браузер не попадают ни при каких условиях.
4. **Адаптер полон.** Даже заглушка реализует все четыре операции, включая возврат.
5. **Остаток честен.** Списание уменьшает ровно на количество, отрицательным не бывает.

## Работа без боевого ключа площадки

Клиент площадки по умолчанию в режиме сухого прогона: запросы не уходят,
намерения пишутся в журнал (`GET /api/marketplace/journal`, после входа в кабинет). Так синхронизация
разрабатывается и проверяется до получения доступа.

Включение боевого режима: задать `MARKETPLACE_CLIENT_ID` и `MARKETPLACE_API_KEY`
в окружении и снять `marketplace.dryRun` в конфигурации. Первые обращения — только
на чтение.

## Развёртывание

`render.yaml` описывает оба сервиса: серверный контур и статику. Витрина сама
узнаёт адрес API. Секреты задаются в интерфейсе площадки размещения.
